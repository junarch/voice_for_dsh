可执行 ✓

架构与槽位选型均与源码契约吻合,发现 6 项疏漏 / 4 项不合理,无颠覆性问题。

现成适配器

设置 Tab(需求 1)

原生支持 ✓

settings.section 槽 = 设置面板导航中的独立一页,带 id/order/label,正是你要的"tab"。

⚠️ 本轮最重要的一个新发现(PLAN 未覆盖)

PLAN 假设"外部 TTS 走 Host 半 fetch(经 ctx.web 或 Node fetch)"。源码核实:ctx.web(dsh-web 的 WebRuntime)只支持 GET 式 URL 抓取(WebFetchRequest 仅有 url 字段,响应体只有 html/text 两种 kind)——无法 POST、无法自定义鉴权头、无法读二进制音频。且创造模式动态插件的 Host 沙箱把全局 fetch 陷阱为抛错("declare inject: ['web'] and call ctx.web")。

✅ 解法:正式 bundle 的 Host 半是普通 Node 模块,不经沙箱,可直接用全局 fetch(Node 18+ undici)调用火山 HTTP 接口。但创造模式动态插件原型无法试验 TTS 外呼——原型阶段 TTS 只能先用浏览器 speechSynthesis 验证链路,火山调用留到正式包阶段验证(或把外呼逻辑放在一个本地独立脚本里先单独冒烟)。

1. PLAN 审查:疏漏与不合理

1.1 疏漏(计划中缺失,需要补)

#严重度疏漏点说明与影响建议
G1高出网通道假设错误如上节所述,ctx.web 只有 GET 抓取能力,POST+鉴权头+音频二进制的 TTS 调用走不通;动态沙箱里 fetch 被禁。PLAN §D4 与风险表未覆盖。正式 bundle Host 半用 Node 原生 fetch;在 §1.4 与 D4 中更正;创造模式 spike 不含 TTS 外呼。
G2高TTS 抽象粒度不足PLAN 的 tts.mode: browser|http + "URL 模板 {text} 占位符"无法表达真实供应商差异:火山的请求体是嵌套 req_params,响应是 chunked JSON 行 + base64 音频段,根本不是"换个 URL"能覆盖的。不同供应商在文本格式、情绪标签、音色 ID 体系、采样率上完全不同(这正是你提的需求 2)。升级为 TTS Provider 适配器架构:统一接口 synthesize(text, opts) → audio,按 provider(browser / openai-compatible / volcengine)分别实现;settings schema 按 provider 分组(见 §6)。
G3中敏感凭据存储未设计火山 API Key 放哪?settings.yaml 明文?PLAN 只字未提。采访已确认:与现状一致放 settings.yaml 明文可接受,但要在文档中写明安全提示。schema 加 voice.tts.volcengine.apiKey;README 加"settings.yaml 为明文文件"提示。
G4中转写语言写死中文docs/voice-pipeline.md 的 system prompt 写死"改写为中文口语文稿",英文会话会被错误翻译成中文播报。采访确认跟随会话语言:prompt 改为"输出与原文相同语言的口语文稿"。
G5中长文本分段策略缺失云 TTS 单次请求有文本长度上限(火山接口通常按句/段处理);一篇长回答的转写稿可能超限。PLAN 无分段合成/拼接设计。另:整段串行(转写→合成)首音延迟 10–30s,采访确认 v1 可接受,但要在文档写明。v1:超长时按段落切分串行合成、顺序播放;v2 再考虑流式 WS。
G6中成本控制缺失云 TTS 按字符计费,自动播报每轮都花钱。PLAN 无任何防护。采访确认:加 voice.autoSpeakCloudTts 开关,默认关——云 TTS 默认只允许手动按钮触发。
G7低Phase 1 checklist 与风险表不一致风险表第 1 条说"Phase 1 先用创造模式做最小 Host 半试验确认 ctx.llm",但 Phase 1 的勾选项里没有这个 spike 步骤。Phase 1 开头加 spike 勾选项(ctx.llm / 槽位注入 / host.call 三项验证)。

1.2 不合理(计划中有,但设计欠妥)

#条目问题修订建议
U1外部 TTS = "OpenAI 兼容 /audio/speech 或自定义 URL 模板"URL 模板方案对真实供应商基本不可用(见 G2),属于伪通用性,还会把架构带偏。删除 URL 模板;改为 provider 枚举 + 每 provider 一个适配器文件。OpenAI 兼容保留(覆盖中转站场景)。
U2音频回传默认 dataURLmp3 经 base64 放大 33%,host.call JSON-only 大 payload 有性能与上限风险;PLAN 自己也把 webserver 路由列为"兜底"。直接以 ctx.webServer 注册 /voice/audio/<id> 临时路由为默认方案,dataURL 仅用于小音频/试听。
U3settings schema 到 Phase 3 才做设置页schema 结构(provider 平铺 vs 分组)一旦写入用户 settings.yaml 再改就是迁移成本;设置页是用户核心需求 1,不应排在最后。Phase 1 就按 provider 分组定好 schema;设置页(settings.section)从 Phase 3 提前到 Phase 2。
U4验收标准未含新需求用户已明确:设置 Tab 可视化配置、火山引擎支持。验收标准 8 条均未覆盖。补 2 条:设置页可完成火山配置并试听成功;火山 provider 冒烟(手动朗读一条消息出声)。

2. 火山引擎 TTS 调研(基于官方 PDF《接入语音模型》)

来源:你下载的火山方舟文档(对应 console.volcengine.com/ark/.../docs/82379/2516286),已提取存档于 docs/research/volcengine-ark-speech.txt(34 页)。该页是方舟 Agent Plan 语音模型接入,TTS 部分要点:

模型与鉴权

  • 模型:豆包语音合成模型 2.0(doubao-seed-tts-2.0)
  • 请求头 X-Api-Resource-Id: seed-tts-2.0
  • 鉴权:X-Api-Key: <方舟专属 API Key>(新版控制台获取,与旧版 appid/token 体系不同)
  • 音色示例:zh_female_gaolengyujie_uranus_bigtts、zh_female_vv_uranus_bigtts
  • 音频参数:format: mp3、sample_rate: 24000、enable_timestamp

三种接入方式对比

方式协议/端点适用
v1 推荐 HTTP 单向POST https://openspeech.bytedance.com/api/v3/plan/tts/unidirectional一次发全文,chunked JSON 行返回 base64 音频段;最简单
WS 单向流式wss://.../v3/plan/tts/unidirectional/stream长文本播报,流式收音频
WS 双向流式wss://.../v3/plan/tts/bidirection实时对话低延迟;需实现官方二进制协议(protocols.py)

HTTP 单向接口:请求/响应结构(自研适配器的全部工作量)

// 请求
POST https://openspeech.bytedance.com/api/v3/plan/tts/unidirectional
Headers: X-Api-Key, X-Api-Resource-Id: seed-tts-2.0, Content-Type: application/json
Body: { "req_params": { "text": "...", "speaker": "zh_female_vv_uranus_bigtts",
        "audio_params": { "format": "mp3", "sample_rate": 24000 } } }

// 响应:Transfer-Encoding chunked,每行一个 JSON:
//   { "code": 0,        "data": "<base64 音频段>" }   ← 音频分片,累加
//   { "code": 20000000 }                                ← 结束帧
//   { "code": >0 其他 }                                 ← 错误
// 全部 base64 段拼接解码 → 完整 mp3
⚠️ 情绪标签:这份"接入语音模型"文档的 req_params 中没有情绪/语气参数。seed-tts-2.0 的情绪控制能力存在于另一套文档(语音合成大模型 v1/v3 接口),是否可用、字段名是什么需要另行查证 —— 你已确认 v1 "只要多音色选择即可",此项列入 §7 待确认,不阻塞。

与本插件的对接点(火山 provider 数据流)

转写文稿→ Host: fetch POST(火山 HTTP 单向)→ 拼接 base64 段 → mp3 Buffer→ ctx.webServer 临时路由 /voice/audio/<id>→ Client <audio src> 播放

调研结论(需求 2 的回答)

不存在"现成可复用且支持火山引擎 v3 接口"的 JS TTS 适配器库。支持火山的实现都是应用内代码(xiaozhi-esp32-server、MiGPT、OpenClaw skills 等),且多基于旧版接口;JS 生态的统一 TTS 库(lobe-tts)不含火山。你指出的"不同供应商文本格式/情绪标签要求不同"非常准确 —— 这正是没有统一库能覆盖长尾供应商的原因,也是本插件应该自建 provider 抽象的证据。

4. 依赖可行性评估:npm 依赖 vs vendored vs 自研(需求 3)

你问的"用和 dsh 一样的 vendor 还是另一种形式"——dsh 自身插件的形态是:Client 半禁止 import/require,依赖只能打包(vendored)进产物;Host 半正式 bundle 是普通 Node 模块,可用 npm 依赖。三条路线对比:

路线做法优点缺点评 verdict
A. npm 依赖第三方适配器 package.json 加 lobe-tts 之类,Host 半 import 省代码 ① 无候选支持火山 v3;② 为 browser/OpenAI 两个简单 provider 引库不值;③ 库自己的依赖树进入 dsh profile,升级/审计负担;④ Host 正式 bundle 虽能 import,但 dsh 插件生态惯例是轻依赖 不推荐
B. vendor 第三方代码进仓库 把 xiaozhi 的 doubao 适配器等代码抄进来改 可控、无外部依赖 Python 代码没法直接用;协议细节仍以官方 PDF 为准,"抄"的价值仅限于参考 仅作参考
C. 自研薄适配层(插件内建) 插件内定义 TtsProvider 接口 + 3 个实现(browser 透传 / openai-compatible / volcengine),火山 HTTP 适配约 100–150 行,零新增依赖 ① 火山 v3 接口本身极简(一个 POST + 行解析);② 完全匹配 settings 分组 schema;③ 无供应链风险;④ 后续加 provider = 加一个文件 协议变动要自己跟(缓解:接口面小,且有官方 PDF 存档在仓库里) ✅ 推荐

推荐架构(自研薄适配层)

src/host/tts/
├── types.ts              # interface TtsProvider { id; synthesize(req) → {audio: Buffer, mime} }
├── browser.ts            # 透传:返回文稿给 Client,speechSynthesis 播报(零出网)
├── openai-compatible.ts  # POST {baseURL}/audio/speech(可接 new-api 等中转)
└── volcengine.ts         # POST v3/plan/tts/unidirectional,逐行解析 base64 → mp3
# Provider 注册表 + settings 里的 voice.tts.provider 选择;新增供应商 = 加一个文件

这条路线的实质是:vendor 的不是别人的库,而是"接口定义 + 每供应商一小段协议代码",与你说的"dsh 式 vendor"精神一致(插件自包含、无外部运行时依赖),同时避免了 npm 依赖的重与失配。
