# 如何测试语音插件（写给非专业开发者的管线测试手册）

> 回答的问题：**"除了自己手动点、用耳朵听，我怎么知道内部管线到底正不正常？"**
> 真实教训：另一个项目里 AI 写的转写代码每条消息悄悄转写 4 次，用了很久直到 token 账单爆了才发现。
> 手动使用之所以发现不了这类问题，是因为**表面现象（有声音、内容大致对）掩盖了内部事实（调了几次、花了多少、走了哪条分支）**。

## 0. 核心心法（先记住这四句）

1. **不问"听起来对吗"，问"每一步发生了什么、发生了几次"。** 把"听感"换成可数的指标：LLM 调用次数、TTS 请求次数、缓存命中率、返回的错误码。
2. **每个外部接口都是不可信的。** 文档会过期、记忆会出错、接口会变。对"接口应该怎么表现"的每个假设，要么用小实验证实，要么在代码里防御。本文的 `[#...]` 标签事故就是"信了 PDF 描述、没实测"的直接后果。
3. **发现的事实要固化成可重复的检查。** 实验结论写进文档会过期，写成断言（测试）就不会。`scripts/test-host.mjs` 里的每条断言都对应一个真实踩过的坑。
4. **断言分两类，别混着信（2026-08-20 新增，起因是你的质疑）。** "不变量"是我们代码自身的要求，放心长期信；"外部事实快照"是对别人接口某天行为的记录，**可能错、会过期**--推翻它必须先拿新证据（跑探针、亲耳听），再同步更新断言+实现+文档三处。测试文件里两类断言用醒目注释分开了。

## 1. 先画管线地图（知道要测什么）

```
[DeepSeek 输出完成] 
   -> Host 监听 session 事件（turn/end, reason=completed/max-tokens）
   -> 提取该轮最后一条含 text 的助手消息
   -> LLM 口语化转写（独立调用，prompt 由风格预设/语种（方言）拼出；简报模式 readMode 已移除）
   -> 转写稿缓存（provider/model/prompt/effort 四者一致才命中）
   -> TTS：browser=客户端 speechSynthesis ｜ 云=Host 合成 + 一次性音频路由
   -> 浏览器播放
```

每一步都有独立的失败方式：事件没触发、消息提取错、转写失败/超时/撞顶、缓存没命中（重复烧钱）、TTS 报错、播放失败。**测试就是逐段验证，而不是只测最后一环。**

## 2. 四层测试手段（从便宜到贵）

### 第 1 层：零成本——mock 集成测试 `scripts/test-host.mjs`

```powershell
node scripts/test-host.mjs
```

- **完全新手也能跑**：VS Code 打开仓库 -> 顶部菜单"终端"->"新建终端"（快捷键 Ctrl+`）->
  输入上面那行命令 -> 回车。测试文件开头有写给第一次接触代码者的完整教学注释
  （.mjs 是什么、mock 是什么、断言怎么读、失败了怎么办），按顺序读即可。
- **不启动 dsh、不开浏览器、不花一分钱**：用 mock 的 llm/sessions/settings/fetch 加载真实的 `lib/index.js`，驱动完整链路。
- 已固化 149 条断言，每条对应一个历史坑：TTS 请求不得含 `[#...]` 标签、数值参数映射正确、**同一消息重复朗读 LLM 调用数不变**（就是防"转写四次"那类事故）、撞顶 4 倍重试、失败降级、自动播报门控、context_texts 指令组装、音色↔语种归一、重播零 LLM、regen 重新生成、WS 兜底……
- 断言分「A 类·不变量」与「B 类·外部事实快照」两组（见文件内醒目注释）：A 类放心长期信；
  B 类是对火山接口某天行为的记录，推翻前必须先跑探针拿新证据。
- **什么时候跑**：每次改完 Host 半代码之后；AI 帮你改完代码之后（让它自己跑给你看结果）。
- **怎么加用例**：照抄现有 `section()` 块的模式——设 `llmState.responses`（模拟 LLM 输出）或 `fetchState`（模拟 TTS 响应），调 `rpc('方法名', 参数)`，用 `check()` 断言。

### 第 2 层：零成本——直接打 RPC 接口（dsh 运行中时）

Host 半暴露的所有能力都是 HTTP 接口，不需要浏览器就能验证：

```powershell
# 存活 + 配置读取
curl.exe -s -X POST http://127.0.0.1:3080/voice/api/ping
curl.exe -s -X POST http://127.0.0.1:3080/voice/api/getConfig

# 元数据（音色/预设清单；确认设置页下拉的数据源）
curl.exe -s -X POST http://127.0.0.1:3080/voice/api/meta

# 朗读指定消息（真实转写，花 token；speakLatest 已移除——speak 需带 sessionId+messageId）
#   curl.exe -s -X POST http://127.0.0.1:3080/voice/api/speak -H "Content-Type: application/json" -d '{"sessionId":"<sid>","messageId":"<mid>"}'
# 试听（云 TTS 花几分钱；browser 引擎则只回文稿）
curl.exe -s -X POST http://127.0.0.1:3080/voice/api/preview
# 重新生成（跳过转写缓存，用当前配置重新转写+合成）
#   curl.exe -s -X POST http://127.0.0.1:3080/voice/api/speak -H "Content-Type: application/json" -d '{"sessionId":"<sid>","messageId":"<mid>","regen":true}'
```

看返回 JSON 的关键字段：`cached`（true=缓存命中没花钱）、`degraded`（true=转写失败走了兜底）、`ttsError`（云 TTS 失败原因）、`audioUrl`（云 TTS 成功）。**这比听声音信息量大得多。**

### 第 3 层：几分钱——真实外呼探针 `scripts/tts-probe.mjs`

```powershell
node scripts/tts-probe.mjs            # 读 settings.yaml 里的 apiKey
node scripts/tts-probe.mjs --key xxx  # 或显式给 key
```

对火山 TTS 做受控实验：同样的短句，分别加内嵌标签/context_texts 指令/数值语速，**每个 case 都保存 mp3 到 `tmp\probe-<时间戳>\`**，跑完按提示打开文件夹逐个试听。时长对比只能证明"标签被照读/数值参数生效"这类强信号；**语气、音色、方言这类只有人耳能判断的效果，必须听音频**。`[#...]` 标签事故和 context_texts 通道的调研（2026-08-19/20，详见 docs/voice-pipeline.md §2.3）都是它实锤的。**怀疑任何外部接口行为时，先跑探针再改代码。**

### 第 4 层：手动验收（最贵，只测前三层测不到的）

浏览器里：设置页渲染、下拉/滑块交互、朗读按钮状态机、自动播报节奏、方言试听。**只在这一层测"人能感知"的东西**，其余交给前三层。

## 3. 账单防御（你的核心痛点）

"转写四次"类问题的共同特征：**功能表面正常，成本暗中异常**。防御手段：

1. **调用计数**：mock 测试里断言"重复朗读不增加 LLM 调用"（test-host.mjs T3 已固化）。
2. **缓存审计**：`%USERPROFILE%\.dsh\voice-transcript-cache.json` 里每条记录含 `at`（时间戳）、`provider/model/prompt`。同一条消息出现多条不同 `at` 的记录 = 有重复转写（合理原因：改了配置；不合理 = bug）。
3. **降级可见性**：`degraded=true` 时设置页/按钮会提示"转写失败已直读"——降级是好事，但**静默降级是账单刺客**，务必让它有声音。
4. **控制台日志**：Host 进程日志里每个关键分支都有 `[voice]` 前缀日志（auto-speak pending / skipped: gated / transcribe failed / cloud tts failed）。测试时开着看，异常分支一目了然。
5. **供应商用量页**：每周扫一眼火山/DeepSeek 的用量曲线，和平时的形状对比——这是最后防线。

## 4. 怎么和 AI 协作做这些（进阶方法）

- **让 AI 先写测试再改代码**： prompt 模板——"先读 docs/testing-guide.md 和 scripts/test-host.mjs，为你要改的行为加断言，跑通后再改实现，改完再跑一遍给我看两轮结果"。
- **要求 AI 报告"调用次数"而不是"我测过了"**：AI 说"测试通过"没有意义，让它贴出 `node scripts/test-host.mjs` 的完整输出。
- **外部接口假设必须给证据**：让 AI 引用接口行为时问一句"这是实测还是推测？"——探针脚本就是为此存在的，让 AI 跑探针并把输出贴给你。
- **每个 bug 修复后问一句**："这个坑怎么变成一条断言？"（例：今天的标签事故变成了 test-host.mjs T6 的"请求 text 无 [# 标签"断言）。
- **git 是你的时光机**：改坏了一键回退。修复前先 `git status` 确认干净，修复后 `git diff` 逐行看 AI 改了什么（哪怕看不全懂，看"改动范围是否符合预期"也能拦住大部分事故）。

## 5. 两次事故的完整复盘（方法论示范）

### 事故一：内嵌 [#...] 标签被照读（2026-08-19）

1. **现象**：暧昧风格播报把 `[#压低声音、带着温柔的笑意说]` 读出来了。
2. **不猜，先取证**：查 `voice-transcript-cache.json`，确认转写稿里确实有这个标签（问题定位在"标签进入了 TTS 文本"，而不是"转写错了"或"播放器错了"）。
3. **对外部接口做受控实验**：tts-probe 对同一文本 ±标签对比时长 → 实锤"接口不解析标签、照读"；顺带发现连现有代码的 `[#上文]` 前缀也在被照读（潜伏 bug），以及数值 `speech_rate` 真的生效（正确修法）。
4. **修架构而不是修表象**：不是"让 LLM 别输出这个标签"就完了——(a) 预设 prompt 不再要求插标签；(b) Host 兜底剥离一切 `[#...]`；(c) 语速/音调改走数值参数；(d) 删掉所有 `[#...]` 注入。
5. **固化**：每条修法都变成 test-host.mjs 的断言 + voice-pipeline.md 的实测记录。

### 事故二：结论被用户质疑后，调研是如何升级的（2026-08-20，这次的主角是你）

1. **你的质疑是对的，哪怕结论碰巧没错**：你指出时长推算不可靠、要求看请求结构、给出旧项目代码。我读了旧项目——它的注释写着「plan 端点不认内嵌 [#指令]（会直读标签文本），提取走官方 context_texts 通道」——**和你给我的代码一致**，于是结论从"我的一家之言"变成"两个独立项目互证"。
2. **发现遗漏的能力**：旧项目用 `additions.context_texts` 传指令。我用新探针（保存 mp3 供试听）验证：内嵌标签确实照读（D 实验时长 2.37 倍）；context_texts 指令**有效果但极不稳定**（vv 音色上多数字面零效果、组合措辞 +10%；xiaohe 上 +15%~49%）。于是插件改为：指令走 context_texts（免费无害、尽力而为）+ 文稿措辞仍是可靠主路径。
3. **我自己的方法论失误（教科书级反例，正说明你的担心）**：第一版探针我比较了文件**大小**就宣称"字节级相同，指令无效"——CBR 码率 MP3 相同时长必然同大小，**哈希一查全不同**！若我当时把"字节级相同"写成断言，就会把错误结论固化。教训：**断言必须贴着原始证据（哈希/音频/次数），推理链每步都要能被推翻**——这正是你第 3 条意见的原话。
4. **落实为制度**：test-host.mjs 把断言分成「A 类·不变量」与「B 类·外部事实快照」；B 类注释写明证据来源和推翻流程（先跑探针 → 再改断言+实现+文档三处）。
5. **等你来收尾的下一步**：试听 `tmp\probe-*` 音频，判定 context_texts 指令到底值不值得保留——你听到的结论将决定 B 类断言是保留、修改还是删除。
