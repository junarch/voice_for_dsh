# 开源发布新手指南（傻瓜版）

> 给"第一个开源项目"的你。目标：**把你的 `voice_for_dsh` 插件以 MIT 协议发到 GitHub，
> 别人能装、能用、能看懂，出了问题知道怎么找你，你也有办法体面地接住**。
> 不需要你懂 git 原理，照着一步步做就行。配套清单见 `docs/release.md`。

## 0. 先搞懂几个词（五分钟）

| 词 | 人话解释 |
|---|---|
| 仓库（repo） | 你的项目在 GitHub 上的"文件夹"，可以是一个项目，也可以是一个仓库装多个包 |
| fork | 别人把**你的仓库**复制一份到他自己名下（他在自己那份里改，不影响你） |
| star | 别人给你点收藏/点赞，表达"这项目不错" |
| issue | 别人给你提的"问题单"：报 bug、提需求、问用法，都在这里 |
| PR（pull request） | 别人改完了，请求把你的代码"拉进"你的仓库（提交贡献） |
| README.md | 仓库首页，别人第一眼看到的东西，相当于项目说明书 |
| LICENSE | 授权协议。你选的 **MIT** = 别人可以随便用、改、商用，只要保留你的版权声明 |
| tag / release | 版本号（如 `v0.1.0`）和一个"发布快照"。release = tag + 说明文字 + 可选打包文件 |
| main 分支 | 默认主分支，一般只放"能稳定发布的版本" |
| CHANGELOG.md | 更新日志，记录"这个版本改了什么" |

## 1. 你问的：还没上传到 GitHub，能 clone 安装吗？

**clone = 从 GitHub 把仓库整个下载到本地**。没上传就没有"远程地址"，所以**别人没法 clone 你**——这不是问题，发布后自然就有了。

那"开发期的安装"怎么理解？

- 你现在装的 `dsh-plugin-voice`，用的是**本地路径**：`dsh plugin --profile web add link:../packages/dsh-plugin-voice`，
  意思"从我电脑这个路径加载插件"。这条路不需要 GitHub。
- **clone 是给"别人"用的**：别人在 GitHub 看到你的项目 → 点绿色 `Code` 按钮复制地址 →
  `git clone https://github.com/你/voice_for_dsh.git` 下到他自己电脑 → 再按你的 README 安装。
- **发布前，你可以自己模拟"别人 clone"**：把整个仓库复制到一个全新的空文件夹（不带你的个人信息），
  然后完全按 README 的安装步骤走一遍。能走通，才说明别人 clone 下来也装得上（见 release §3）。

> 一句话：**开发用本地路径，发布给别人用 clone。clone 这件事在你上传 GitHub 之后自然成立。**

## 3. 第一次发布：把代码推上去

1. **建仓库**：GitHub 网页右上角 `+` → New repository → 名字 `voice_for_dsh` →
   Public（要开源就是 Public）→ 不要勾选 "Add a README"（本地已有/将有，避免冲突）→ Create。
2. **本地连上远程**（在仓库根执行一次）：
   ```
   git remote add origin https://github.com/你的用户名/voice_for_dsh.git
   git branch -M main
   git push -u origin main
   ```
3. **打第一个版本 tag**：
   ```
   git tag v0.1.0
   git push origin v0.1.0
   ```
4. **写 release**：GitHub 仓库页 → Releases → Create a new release → 选 `v0.1.0` →
   标题 `v0.1.0`，正文写"初版发布：支持 XX"，可附截图 → Publish。

> 之后每次发版就是：`git tag vX.Y.Z` + `git push origin vX.Y.Z` + 在 Releases 页面写说明。
> 版本号规则见 §4。

## 4. 日常维护：怎么"更新"一个开源项目

### 4.1 版本号（三格数字 x.y.z，叫 SemVer）

- **x 大版本**：破坏性变更（配置不兼容、行为大变）→ 1.0 → 2.0
- **y 中版本**：加新功能（向后兼容）→ 0.1 → 0.2
- **z 小版本**：修 bug / 小改进 → 0.1.0 → 0.1.1

发布流程（每次都是这套）：
```
1. 改代码（本仓库）
2. 跑测试：node scripts/test-host.mjs   # 必须全绿
3. 更新 CHANGELOG.md
4. git add 相关文件 && git commit -m "feat(voice): 说明改了什么"
5. git push
6. 决定要不要发新版本：git tag v0.2.0 && git push origin v0.2.0
7. GitHub Releases 写说明
```

### 4.2 提交信息怎么写（让历史可读）

简单格式：`类型(模块): 一句话`。比如：
```
feat(voice): 支持自动播报开关
fix(voice): 修复换音色后重播串音
docs: 补充安装说明
test: 为重复朗读加断言
```
你 git 里已经在用 `feat(voice): ...` 这个风格了，保持就好。

### 4.3 别干这些事

- ❌ **别直接往 main 上乱改还不测试**——main 应该是"能发布的稳定版"。测试放开发分支或提交前跑。
- ❌ **别 force push（强推）** `git push --force`——会覆盖历史，破坏别人已 clone 的副本。能不用就不用。
- ❌ **别在 main 上直接改 README 当"随手存"**——改动要能说清"为什么"。

## 5. 面对 issue 和 PR：社区规则的"人情世故"

> 核心心态：**这是你的项目，你有决定权；但对来帮忙的人要尊重、要回应、要有边界。**

### 5.1 收到 issue（问题单）

新手三步：
1. **先回一句"收到，我看看"**（哪怕当天不解决）——用户最怕的是石沉大海。
2. **分类**：
   - 报 bug → 让他给环境信息（DSH 版本、Node 版本、浏览器、settings.yaml 里的 voice 配置、报错日志）。
     复现不了就照 `docs/testing.md` 让他开 `[voice]` 日志、看 `voice-transcript-cache.json`。
   - 提需求 → 判断值不值得做。不做就**礼貌说明理由并关闭**（"暂不考虑，因为……"），比拖成僵尸 issue 好。
   - 问用法 → 直接答，答完把答案补进 README（"好问题，我加到文档里了"——这是高质量维护者的习惯）。
3. **用标签管理**：`bug`、`enhancement`、`question`、`good first issue`（适合新人练手）、`help wanted`。
   不想做的就标 `wontfix` 或直接关闭并说明。

> 一个有用的习惯：在 issue 里 @ 自己开的 AI 助手，让它帮忙先复现、先取证，再谈修复——你已经在用这套流程了。

### 5.2 收到 PR（别人给你贡献代码）

1. **先看 CI**（如果配了 GitHub Actions）：自动跑 `node scripts/test-host.mjs`，红了先让作者修，别急着合。
2. **人工 review**：改动小可以直接合；改动大就逐行看。看不懂就**问**，别不好意思（"这个改动的动机是什么？"）。
3. **合并方式**：单人维护、想保持历史干净 → 点 "Squash and merge"（把多个提交压成一个，写清一条 message）。
4. **合完必做**：在 PR 里回一句"谢谢你的贡献！已合并，会在 vX.Y.Z 发布"。
5. **不合的时候**：说明理由（"设计上我们打算……"，"这部分超出插件范围"），语气保持尊重，然后关闭。
   **MIT 项目里，贡献者的代码一旦合并进你的仓库，也要保留其版权**——所以贡献者通常要明确同意协议（PR 提交即表示同意按 MIT 授权）。

### 5.3 铁律（社区规则速记）

- 对任何人都礼貌、就事论事，不人身攻击。
- 不 star 求 star、不刷屏推广（偶尔在相关社区提一句可以，别到处硬广）。
- 承诺的事情要做到；做不到就更新 issue 说明现状。
- 别人的 fork/star 是认可，不是你的义务来"回关"。
- 你的时间有限，README 里可以写明："业余维护，issue 回复可能慢"——这是合法的免责，也是诚实的边界。

## 6. 成本与隐私声明（对用户负责，必写进 README）

你的插件**会把用户的对话内容发给第三方**，必须明说，这是开源项目的良心问题：

- **转写**：走用户的 LLM 提供商（DeepSeek/阿里云等，settings.yaml 里配的），**每次转写花 token**。
- **TTS**：浏览器语音免费；豆包 TTS 走火山引擎，按字符/时长计费。
- **免费点**（你的卖点，要写出来）：重播同一消息 1h 内走服务端缓存**免重合成**；
  转写结果有本地缓存，同消息不重复转写。
- **隐私**：README 明确"你的对话内容会发送给所配置的第三方 LLM/TTS 服务，请谨慎在敏感会话使用"。
  建议默认**不开自动播报**，让用户自己选择何时朗读。

## 6.5 发布前准备实录（这轮我们做了什么、为什么）

> 你可能看不懂"153 条测试""git grep""CI 自动跑"这些词。这一节专门用大白话解释：
> **每件事是什么、为什么发布前必须做。** 有不清楚的，随时在这个"提问 session"里问我。

### ① "153 条测试"是什么？为什么是个好东西？

- **人话**：这是一份"自动体检报告"。它不用打开网页、不用点按钮、不花一分钱 API 费，
  一秒左右就把插件的"服务端半"（Host 半）从头到尾检查 153 项。
- **它防的是你最大的噩梦——浪费 Token**：比如"同一消息重复朗读却偷偷调了 4 次大模型"，
  这种 bug 光靠耳朵听**绝对发现不了**（声音正常、内容对，但账单在烧钱）。
  测试里有一条专门盯着它：`同一消息重复朗读，LLM 调用次数不许增加`。
- **怎么跑**：在仓库根目录终端输入 `node scripts/test-host.mjs`，看到
  `结果: 153 passed, 0 failed` 就是全绿。测试文件开头的注释是**写给新手看的完整教学**，
  从"这是什么文件"开始讲，你可以打开 `scripts/test-host.mjs` 读前 50 行。
- 这些断言还分两类（详见 testing §0）：**A 类·不变量**（我们自己代码必须永远满足的规矩，
  比如"不得烧重复 token"）放心信；**B 类·外部事实快照**（对火山接口某天行为的记录）可能过时，
  一旦失败要先跑探针拿新证据再改，不能自己偷偷把断言改绿。

### ② "git grep 密钥自查"是什么？为什么必须做？

- **人话**：git grep = "在仓库所有代码里搜内容"。密钥自查 = 搜一下代码里有没有
  `sk-`（火山/大模型 API Key 的开头）、`apikey`、`api_key` 这类字符串。
- **为什么必须**：你一旦把仓库公开到 GitHub，**所有人**都能看到里面每一个字。
  如果你不小心把真实的 API Key 写进代码并提交过，等于把"能花你钱的密码"贴在了大街上——
  别人拿去能直接用你的额度，账单找你。而且**就算你后来删掉了，git 历史里还留着**，一样算泄露。
- **怎么做**（发布前在仓库根执行）：
  ```
  git grep -n "sk-\|apikey\|api_key"
  ```
  有结果就说明有嫌疑，逐个排查；顺便用 `git log` 看历史里有没有提交过含密钥的文件。
- **万一真泄露过怎么办**：去对应平台（火山/DeepSeek/阿里云）**立刻吊销那个 key、换新 key**——
  这是第一优先，比清理历史还重要（历史清理方法见 §7 FAQ）。

### ③ "CI 自动跑 153 条断言"是什么？为什么能替你省事？

- **人话**：CI（Continuous Integration，持续集成） = 你委托 GitHub 的一台"免费机器人"。
  只要你把代码推到 GitHub（自己 push 或别人提 PR），机器人就自动：
  checkout 代码 → 装依赖 → 跑那 153 条测试 → 把"绿了/红了"直接显示在网页上。
- **为什么好**：
  1. **别人提 PR 时**：你不用手动催他"你跑测试了吗"，PR 页面上自己会显示测试红绿，
     红了就让他改，绿了才合并——这是开源项目最基本的"守门"。
  2. **你自己改代码时**：push 上去就知道有没有改坏，不用每次都记得在本地跑。
  3. 它是**零成本**的（GitHub 对公开仓库免费），且跑的是零成本的 mock 测试，**不花你的 API 钱**。
- **本仓库已经配好**：`.github/workflows/test.yml`（已在本地验证 npm ci 能装依赖、
  test-host 能全绿）。为什么用 Node 22：代码用了 Node 22 才有的全局 WebSocket，更低版本装不了。
  这个文件发布后就会自动生效。

## 7. 常见问题（FAQ）

**Q：以前误提交过密钥到 git 历史，现在删了还有事吗？**
A：有事。历史里删不掉（除非清洗）。GitHub 会给所有历史里的内容发"密钥泄露"通知。处理：
1. 立刻去对应平台（火山/DeepSeek/阿里云）**吊销并换新 key**；
2. 用 `git filter-repo` 清洗历史（或直接 `rm -rf .git` 重新 `git init`——你还没发布，最省事的就是这个，
   但会丢提交历史，二选一权衡）；
3. 以后把 key 放 settings.yaml（已被 .gitignore 忽略）。

**Q：要不要配 GitHub Actions（CI）？**
A：**已经配好了**——本仓库根 `.github/workflows/test.yml`。发布到 GitHub 后自动生效：
每次 push 或别人提 PR，机器人自动跑 153 条测试，红绿直接显示在 PR/提交页（详见 §6.5 ③）。

**Q：别人 fork 了会怎样？**
A：只是他在自己名下多一份副本，不影响你。他改完要回馈你，才会提 PR。

**Q：有人乱提 issue / 广告 spam？**
A：标记为 `invalid` 或直接关闭并可选 block。GitHub 有举报渠道，一般不严重不用理。

**Q：我不想维护了？**
A：README 顶部写"此项目已归档（archived）"，GitHub 仓库设置里 Archive 掉。比悄悄消失体面。
